## Общие правила, которые действуют на всех восьми защитах

Четыре требования из методички проверяют на **каждой** работе,
независимо от её темы:

1. **Проверка исходных данных обязательна везде.**
   Вас попросят ввести некорректные значения в любое поле.
   Ответ в коде — `src/services/validationService.js`.

2. **Всё, что не задано явно, должно меняться при тестировании.**
   Порт, число карточек на странице, логин администратора —
   всё задаётся переменными окружения, см. таблицу в `README.md`.

3. **Вывод результатов только через элементы на странице.**
   Консоль разработчика используется только при отладке.
   В проекте нигде нет вывода в консоль вместо интерфейса.

4. **Имя файла отчёта строго `8ВМ61_Мальцева_ЕМ_01`.**
   Файл с другим именем не примут, баллы не начислят.

### Про количество попыток

Полный балл возможен только при сдаче с первой попытки.
Перед защитой пройдите сценарий целиком дома.
Вторая попытка автоматически снижает оценку.

## ЛБ 1. Просмотр и переход по ссылкам

**Задание:** реализовать пользовательскую страницу для просмотра
и перехода по ссылкам.

### Что показывать

1. Откройте главную страницу — 9 карточек, у каждой название,
   описание, тема, адрес и счётчик переходов.
2. Покажите постраничную навигацию внизу: 41 ссылка разбита на 5 страниц.
3. Перейдите на вторую и последнюю страницу — адрес меняется на `/?page=2`.
4. Щёлкните по названию ссылки — откроется внешний сайт в новой вкладке.
5. Вернитесь и обновите страницу — счётчик переходов увеличился.

### Что спросят

**«Почему переход идёт через ваш адрес `/go/23`, а не сразу на сайт?»**
Прямая ссылка не позволяет серверу узнать о переходе.
Маршрут `/go/:id` сначала увеличивает счётчик и записывает событие
в журнал, затем выполняет перенаправление с кодом 302.

**«Что произойдёт при вводе `/go/99999`?»**
Ссылка не найдена, выводится страница с кодом 404 и понятным сообщением.

**«Что будет при вводе `/?page=999`?»**
Номер страницы приводится к допустимому диапазону функцией
`normalizePage`, откроется последняя существующая страница.

## ЛБ 2. Фильтрация ссылок по темам

**Задание:** реализовать пользовательскую страницу для фильтрации
ссылок по темам.

### Что показывать

1. Панель тем под фильтрами: 6 тем, у каждой число ссылок.
2. Выберите тему — останутся только её ссылки, заголовок страницы
   сменится на название темы, адрес станет `/?topic=2`.
3. Введите текст в поле поиска — список обновится автоматически
   через полсекунды после окончания ввода.
4. Покажите, что поиск и тема работают вместе: выберите тему,
   затем введите запрос — условия объединяются.
5. Смените порядок вывода в выпадающем списке.
6. Нажмите «Сбросить» — вернётся полный список.

### Что спросят

**«Поиск учитывает регистр букв?»**
Нет. Причём для кириллицы это отдельная задача: встроенная функция
`LOWER()` в SQLite обрабатывает только латиницу. Поэтому в проекте
зарегистрирована собственная функция `RULOWER`, использующая
средства JavaScript.

**«Где выполняется фильтрация — в браузере или на сервере?»**
На сервере, в SQL-запросе. В браузер приходят только подходящие записи.
Если бы фильтрация выполнялась в браузере, пришлось бы загружать
весь каталог целиком.

**«Что если ввести очень длинный поисковый запрос?»**
Строка обрезается до 100 символов функцией `normalizeSearch`.

## ЛБ 3. Просмотр каталога, включая скрытые

**Задание:** реализовать административную страницу для просмотра
каталога ссылок (в том числе — скрытых).

### Что показывать

1. Откройте `/admin` — таблица всех ссылок каталога.
2. Найдите записи с меткой «Скрыта» — их две:
   «Устаревший ресурс (архив)» и «Черновик подборки».
3. Откройте главную страницу сайта и покажите, что этих записей
   там нет — посетитель их не видит.
4. Вернитесь в панель, нажмите «Скрыть» у любой видимой ссылки.
5. Обновите главную страницу — ссылка исчезла из каталога.
6. Верните её кнопкой «Показать».

### Что спросят

**«Как технически реализовано скрытие?»**
Поле `is_hidden` в таблице `links`: 0 — ссылка видна, 1 — скрыта.
В запросах пользовательской части добавляется условие `is_hidden = 0`,
в административной части это условие не добавляется.

**«Почему не удалять записи вместо скрытия?»**
Скрытие обратимо и сохраняет статистику переходов.
Удаление необратимо, поэтому оно вынесено в отдельное действие
с подтверждением.

**«Можно ли перейти по скрытой ссылке, зная её адрес?»**
Нет. Маршрут `/go/:id` проверяет признак `is_hidden` и отказывает
в переходе, записывая попытку в журнал как отказ в доступе.

## ЛБ 4. Добавление и удаление ссылок

**Задание:** реализовать административную страницу для
добавления/удаления ссылок.

### Что показывать, по шагам

**Шаг 1. Открыть форму.**
Панель управления → «Добавить ссылку».
Обратите внимание: поля со звёздочкой обязательны.

**Шаг 2. Добавить корректную запись.**

| Поле | Значение |
|---|---|
| Название | `Тестовый ресурс` |
| Адрес | `example-test.org` — намеренно без схемы |
| Тема | любая |
| Описание | несколько слов |

Отправьте форму. Вернётесь в каталог с сообщением об успехе.

**Сразу обратите внимание преподавателя:** адрес сохранился
как `https://example-test.org/` — схема подставилась автоматически.
Это правило валидации, а не случайность.

**Шаг 3. Показать проверку данных — самое важное.**

Снова откройте форму и введите заведомо неверные значения:

- Название оставьте пустым
- Адрес: `javascript:alert(1)`

Отправьте. Появится блок с двумя ошибками:
«Название не может быть пустым» и
«Допустимы только адреса, начинающиеся с http:// или https://».

**Скажите вслух:** схема `javascript:` заблокирована намеренно,
иначе через каталог можно было бы провести атаку на посетителя.

**Шаг 4. Показать защиту от повторов.**
Добавьте ссылку с уже существующим адресом, например `https://github.com`.
Появится сообщение: «Ссылка с таким адресом уже есть в каталоге: «GitHub»».

**Шаг 5. Удаление.**
В таблице нажмите «Удалить» у тестовой записи.
Появится окно подтверждения с названием ссылки.
Нажмите «Отмена» — запись останется.
Нажмите снова и подтвердите — запись удалена.

### Что спросят и как отвечать

**«Где проверяются данные — в браузере или на сервере?»**

Это главный вопрос по данной работе. Правильный ответ:
**и там, и там, но браузерная проверка не является защитой.**

В файле `src/public/js/admin.js` есть предварительная проверка,
чтобы не отправлять на сервер заведомо пустую форму.
Настоящая проверка выполняется на сервере в `validationService.js`,
поскольку браузерную проверку можно отключить.

**Как это доказать, если попросят.**
Откройте DevTools → Console и выполните:

```javascript
document.getElementById('link-form').noValidate = true;
document.getElementById('title').removeAttribute('required');
```

Теперь отправьте пустую форму: браузер пропустит её,
а сервер вернёт сообщение об ошибке.
Это сильный аргумент, он сразу закрывает вопрос.

**«Почему адрес проверяется классом `URL`, а не регулярным выражением?»**
Регулярное выражение для адреса либо слишком простое и пропускает
некорректные значения, либо громоздкое и нечитаемое.
Конструктор `new URL()` выполняет разбор по стандарту и сразу
даёт протокол и доменное имя отдельными полями.

**«Что если два администратора одновременно удалят одну запись?»**
Второй получит сообщение «Ссылка не найдена»: перед удалением
проверяется существование записи.

## ЛБ 5. Рейтинг ссылок

**Задание:** реализовать административную страницу для отображения
рейтинга ссылок.

### Что показывать

**Шаг 1. Сначала подготовьте данные.**
Это ключевой момент: рейтинг нужно показать «живым».
Перед защитой откройте сайт и несколько раз перейдите
по одной из ссылок — например, по ссылке «Vite».

**Шаг 2. Откройте `/admin/rating`.**
Покажите четыре показателя в верхней части: всего ссылок,
всего переходов, среднее значение, наибольший показатель.

**Шаг 3. Покажите обе диаграммы.**
Верхняя — распределение переходов по темам,
нижняя — доля каждой ссылки в таблице.
Объясните расчёт ширины полосы:
`width = clicks / maxClicks * 100`.

**Шаг 4. Смените количество выводимых записей.**
Выпадающий список 10 / 20 / 50.
Страница перезагружается с новым параметром в адресе.

**Шаг 5. Докажите, что счётчик работает.**
Запомните значение у любой ссылки → перейдите на сайт →
щёлкните по ней дважды → вернитесь в рейтинг →
значение увеличилось на 2.

### Что спросят

**«Откуда берутся эти числа?»**
Поле `clicks` таблицы `links`. Увеличивается в функции
`incrementClicks()` при каждом переходе через маршрут `/go/:id`.

**«Почему переход идёт через ваш адрес, а не напрямую?»**
Прямая ссылка не позволяет серверу узнать о переходе.
Маршрут `/go/23` увеличивает счётчик, записывает событие в журнал
и только затем перенаправляет посетителя.

**«Зачем ограничен список 10/20/50, почему не любое число?»**
Это проверка исходных данных. Если принимать произвольное значение,
пользователь передаст `limit=999999999` и создаст чрезмерную нагрузку.
В коде: `[10, 20, 50].includes(limitRaw) ? limitRaw : 10`.

**«Учитываются ли скрытые ссылки?»**
В административном рейтинге учитываются: администратору важна
полная картина. Такие записи помечены меткой «Скрыта».

## ЛБ 6. Протоколирование действий

**Задание:** реализовать протоколирование действий пользователя
в файле (текстовом, XML, JSON) и дать возможность смотреть перечень
запротоколированных действий в табличном виде (дата, время, действие).

### Что показывать

**Шаг 1. Покажите сам файл.**
Откройте `logs/actions.json` в редакторе.
Формат — JSON Lines: одна запись на строку.

**Почему так, а не единый массив** (вероятный вопрос):
чтобы дописать запись в массив, нужно прочитать весь файл,
разобрать его, добавить запись и записать обратно.
При формате JSON Lines достаточно одной операции добавления в конец.
Кроме того, при аварийном завершении повредится одна строка,
а не весь файл.

**Шаг 2. Покажите страницу `/admin/logs`.**
Методичка требует таблицу с датой, временем и действием —
это первые колонки. Дополнительно выводятся уровень важности,
пользователь и объект действия.

**Шаг 3. Продемонстрируйте запись в реальном времени.**
Откройте вторую вкладку → выполните поиск на сайте →
вернитесь в журнал → обновите страницу.
Вверху появилась запись «Поиск по каталогу».

**Шаг 4. Покажите фильтрацию.**
Выберите уровень «Предупреждение» — останутся только неудачные
попытки входа и отказы в доступе.
Затем отфильтруйте по конкретному действию и по диапазону дат.

**Шаг 5. Покажите словарь действий.**
Откройте `src/services/logService.js`, покажите константу `ACTIONS` —
15 кодов действий.

**Сильный аргумент:** произвольное название действия записать нельзя.
При неизвестном коде функция выводит предупреждение и не создаёт запись.
Это защищает журнал от случайных значений.

### Что спросят

**«Почему JSON, а не текстовый файл?»**
Текстовый файл приходится разбирать регулярными выражениями,
и он ломается, если в данных встретится символ-разделитель.
JSON разбирается штатными средствами и хранит вложенную структуру —
например, объект `target` с идентификатором и названием.

**«Что будет, когда файл разрастётся?»**
Предусмотрена ротация: при превышении 512 КБ файл переименовывается
в архив с меткой времени, хранятся 5 последних архивов.
Значения настраиваются в `config.js`.

**«Что если запись в журнал не удалась?»**
Операция обёрнута в `try/catch`. Сбой журналирования не должен
приводить к отказу всего приложения: пользователь продолжит работу,
сообщение об ошибке выводится в консоль сервера.

**«Кто такой actor в записи?»**
Инициатор действия: `guest` для посетителя, `admin` с указанием
логина для администратора. Дополнительно записывается IP-адрес.

## ЛБ 7. Парольная защита

**Задание:** защитить **все** административные страницы
парольным доступом.

Ключевое слово — «все». Преподаватель будет проверять именно это.

### Что показывать

**Шаг 1. Выйдите из панели управления.**
Нажмите «Выйти» в тёмной полосе вверху.

**Шаг 2. Попробуйте открыть служебные адреса напрямую.**
Вводите в адресную строку по очереди:

```
/admin
/admin/rating
/admin/logs
/admin/links/new
/admin/links/23/edit
```

Каждый раз происходит перенаправление на форму входа.
**Это и есть демонстрация задания** — защищена не одна страница, а все.

**Шаг 3. Покажите, как это устроено.**
Откройте `src/routes/adminRoutes.js`, найдите строку:

```javascript
router.use(requireAuth);
```

Она расположена после маршрутов входа и до всех остальных.
Всё, что описано ниже, защищено автоматически.
При добавлении новой административной страницы забыть о защите
невозможно — она применяется по умолчанию.

**Шаг 4. Покажите возврат на запрошенную страницу.**
Выйдите из системы, наберите `/admin/rating`, вас перенаправит
на форму входа. После входа откроется именно рейтинг,
а не главная страница: запрошенный адрес сохраняется в сессии.

**Шаг 5. Неверный пароль.**
Введите `admin` и произвольный неверный пароль.
Появится сообщение «Неверный логин или пароль».

**Важный момент, скажите его сами:** сообщение одинаково
и для несуществующего логина, и для неверного пароля.
Если бы сообщения различались, перебором можно было бы
установить существующие учётные записи.

**Шаг 6. Защита от подбора.**
Введите неверный пароль пять раз подряд.
На шестой раз появится сообщение
«Слишком много неудачных попыток. Повторите через N с.»

**Шаг 7. Покажите способ хранения пароля.**
Выполните в терминале:

```bash
node -e "const db=require('./src/models/database');console.log(db.prepare('SELECT login,password_hash FROM admins').get())"
```

В базе хранится не пароль, а хеш вида `$2a$10$...`.
Даже получив файл базы, восстановить исходный пароль нельзя.

### Что спросят

**«Чем хеширование отличается от шифрования?»**
Шифрование обратимо: зная ключ, можно получить исходные данные.
Хеширование необратимо. При входе хеш не расшифровывается —
вычисляется хеш введённого пароля и сравнивается с сохранённым.

**«Что такое соль и применяется ли она?»**
Применяется, bcrypt добавляет её автоматически — она содержится
в самой строке хеша. Благодаря соли одинаковые пароли дают разные
хеши, поэтому заранее вычисленные таблицы хешей бесполезны.

**«Где хранится факт входа в систему?»**
В сессии. Браузеру передаётся подписанная cookie с идентификатором,
сами данные хранятся на сервере в файле `data/sessions.db`.
Cookie помечена признаком `httpOnly` — она недоступна сценариям
в браузере, и `sameSite: lax` — защита от межсайтовых запросов.

**«Придётся ли входить заново после перезапуска сервера?»**
Нет, сессии хранятся в базе данных, а не в оперативной памяти.
Это можно продемонстрировать: перезапустите сервер и обновите
страницу панели управления — вход сохранится.

### Сильный ход: расскажите про найденную ошибку

В проекте есть реальная история отладки, и она убедительнее
учебного примера.

При тестировании поиск по слову «Хабр» с заглавной буквы
не находил запись, хотя в базе она есть. Через отладчик удалось
дойти до SQL-запроса и проверить в консоли:

```javascript
db.prepare("SELECT LOWER('ХАБР') v").get()
```

Результат — `ХАБР`, без изменений. Оказалось, что встроенная функция
`LOWER()` в SQLite приводит к нижнему регистру только латинские буквы.
Решение — собственная функция `RULOWER`, зарегистрированная в базе
и использующая средства JavaScript.

Такой пример показывает не знание кнопок отладчика,
а умение применять его для поиска действительной причины ошибки.

### Что спросят

**«Чем точка останова лучше вывода в консоль?»**
Вывод в консоль показывает одно значение в одной точке,
и для каждого нового значения нужно править код и перезапускать
приложение. Отладчик показывает всё состояние сразу, позволяет
выполнять код по шагам и изменять значения во время выполнения.

**«Что такое Logpoint?»**
Точка, которая не останавливает выполнение, а выводит сообщение.
Удобна в циклах, где обычная точка останова срабатывала бы
на каждой итерации.

**«Как отлаживать код, выполняющийся в браузере?»**
Это другой отладчик: DevTools → Sources.
В проекте браузерного кода немного — файлы `catalog.js` и `admin.js`.
Основная логика выполняется на сервере и отлаживается в редакторе.

## Вопросы, которые зададут независимо от номера лабы

**«Почему сайт многостраничный, а не одностраничный?»**
Так требует задание. Каждая страница — отдельный адрес
и отдельный HTTP-запрос, разметка формируется на сервере
шаблонизатором EJS.

**«Покажите архитектуру приложения.»**
Четыре слоя:

| Слой | Назначение | Папка |
|---|---|---|
| Маршруты | приём запроса, выбор страницы | `routes/` |
| Сервисы | бизнес-логика и проверка данных | `services/` |
| Репозитории | обращения к базе данных | `repositories/` |
| Модели | схема данных | `models/` |

**Главный аргумент:** SQL-запросы содержатся только в репозиториях
и нигде больше. Это проверяется поиском по файлам проекта.

**«Как обеспечена защита от SQL-инъекций?»**
Все запросы параметризованные: значения передаются отдельно
от текста запроса через `?` или именованные параметры.
Склеивания строк с пользовательскими данными в запросах нет.

**«Почему SQLite, а не MySQL или PostgreSQL?»**
База хранится в одном файле, не требует отдельного сервера,
проект разворачивается тремя командами на любой машине.
Для учебного каталога из нескольких десятков записей
полноценная СУБД избыточна.

**«Какие внешние библиотеки используются на стороне браузера?»**
Никакие. Оформление выполнено собственной таблицей стилей,
интерактивные элементы — обычным JavaScript без фреймворков.
